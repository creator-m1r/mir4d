# МИР 4D — MirUI UX Specification

**Версия:** 1.0  
**Дата:** 17 августа 2026  
**Статус:** базовый нормативный документ UX/UI  
**Область:** `MirUI` / SwiftUI / macOS  
**Связь:** `MirEngine`, `MirServer`, `AppState`, `Event Bus`, `.mir4d`

---

## 1. Назначение документа

Этот документ фиксирует все принятые требования, принципы и решения по пользовательскому интерфейсу МИР 4D.

MirUI должен скрывать сложность инженерного ядра и показывать пользователю простую, последовательную и контекстную рабочую среду. Пользователь не должен изучать архитектуру программы, чтобы выполнить инженерную задачу.

Главная формула UX:

> **Мощность внутри — простота снаружи.**

---

## 2. Цели MirUI

1. Создать единую инженерную среду МИР 4D.
2. Сократить количество одновременно видимых команд.
3. Сделать основные действия очевидными без обучения.
4. Сохранить доступ ко всей мощности `MirEngine` и `MirServer`.
5. Сделать интерфейс контекстным: команды появляются тогда, когда они нужны.
6. Обеспечить последовательный путь от запуска до готового инженерного результата.
7. Поддерживать 3D, эскизы, B-Rep, сборки, расчёты, 4D и совместную работу без визуального перегруза.
8. Обеспечить macOS-native взаимодействие через SwiftUI.
9. Не связывать UX напрямую с внутренней структурой C++ ядра.

---

## 3. Главный UX-принцип

Пользователь мыслит не подсистемами, а задачами.

Нельзя строить интерфейс вокруг:

- B-Rep;
- Kernel;
- CAE;
- Runtime;
- Event Bus;
- AI Inspector;
- Math Engine;
- Collaboration.

Это архитектурные понятия.

Пользователь должен видеть:

- Создать;
- Открыть;
- Продолжить;
- Нарисовать;
- Построить;
- Изменить;
- Проверить;
- Рассчитать;
- Получить результат.

---

# 4. Структура пользовательского пространства

Основной путь:

```text
Запуск
  ↓
Самодиагностика
  ↓
Project Hub
  ↓
Рабочая область
  ↓
Контекстное моделирование
  ↓
Анализ / расчёт / 4D
  ↓
Результат
```

Возврат:

```text
Рабочая область
  ↓
Сохранить
  ↓
Project Hub
```

Переходы должны быть плавными и сохранять ощущение одного приложения, а не набора независимых окон.

---

# 5. Startup / Boot UX

Стартовая последовательность состоит из двух смысловых этапов:

1. **Boot / Diagnostics** — программа проверяет готовность среды.
2. **Project Hub** — пользователь выбирает действие.

Диагностика должна быть настоящей, а не декоративным progress bar.

`BootCoordinator` отвечает за реальные этапы готовности. UI только визуализирует состояние.

Состояния:

- запуск;
- проверка;
- готово;
- предупреждение;
- ошибка.

Ошибка запуска должна объясняться человеческим языком и предлагать следующий шаг.

---

# 6. Project Hub

Project Hub — главный стартовый экран после успешной диагностики.

Его задача — ответить на вопрос:

> **Что вы хотите сделать сейчас?**

На экране не должно быть десятков равноправных кнопок.

Приоритет действий:

1. Продолжить последний проект.
2. Создать проект.
3. Открыть существующий проект.
4. Выбрать тип нового проекта.
5. Найти недавний проект.
6. Дополнительные возможности.

---

## 6.1 Верхняя панель Project Hub

Верхняя панель должна быть компактной.

Рекомендуемая структура:

```text
МИР 4D                         ● Готово     Открыть  Новый проект
```

Слева:

- логотип;
- название МИР 4D;
- краткое описание при необходимости.

По центру/справа:

- компактный статус диагностики.

Справа:

- дополнительные действия через меню;
- `Открыть`;
- основной CTA `Новый проект`.

Не допускается размещение в шапке множества кнопок одинакового визуального веса.

---

# 7. Главный экран Project Hub

Предпочтительная логика:

```text
С ЧЕГО НАЧНЁМ?

[ Продолжить проект ]

СОЗДАТЬ
[ Деталь ] [ Сборка ] [ Эскиз / Чертёж ]

ПРОЕКТЫ
[ Поиск проекта... ]
[ Проект ] [ Проект ]
[ Проект ] [ Проект ]

Дополнительные возможности
```

### Правило

Не более нескольких главных действий одновременно.

Если функция не является необходимой для первого шага пользователя, она не должна конкурировать с основным CTA.

---

# 8. Продолжение проекта

`Продолжить` — самый быстрый путь в работу.

Если есть последний доступный проект:

- показать имя;
- показать тип рабочей области;
- показать миниатюру;
- показать дату последнего открытия;
- открыть одним действием.

Если проекта нет:

- карточка должна превратиться в понятное состояние `Создайте первый проект`.

---

# 9. Создание проекта

Создание нового проекта должно быть коротким сценарием.

Минимальные параметры:

- имя;
- расположение;
- тип рабочей области;
- при необходимости шаблон.

После подтверждения создаётся реальный `.mir4d` проект.

Нельзя создавать рабочую область как временную иллюзию, которая не имеет проектного состояния на диске.

---

# 10. Формат проекта

MirUI работает с проектным форматом `.mir4d` через проектный слой, а не через прямое управление внутренними файлами ядра.

UI должен получать:

- имя проекта;
- путь;
- статус доступности;
- рабочую область;
- дату открытия;
- превью;
- состояние сохранения.

---

# 11. Недавние проекты

Недавние проекты должны быть визуально компактными.

Карточка проекта:

- thumbnail;
- название;
- тип рабочей области;
- дата;
- индикатор доступности.

Поддерживаются:

- поиск;
- открытие;
- контекстное меню;
- показать в Finder;
- копировать путь;
- удалить из списка недавних.

Недоступный проект не должен выглядеть как рабочий.

---

# 12. Навигация верхнего уровня

Внутри CAD-среды верхняя навигация должна описывать деятельность пользователя, а не внутренние модули.

Базовые области:

```text
Проект | Моделирование | Анализ | 4D
```

Дополнительные функции открываются контекстно или через вторичные панели.

Не следует превращать верхнюю панель в список всех возможностей продукта.

---

# 13. Рабочая область CAD

Рабочая область должна иметь четыре устойчивые зоны:

```text
┌──────────────────────────────────────────────┐
│ Верхняя навигация / контекст                 │
├───────────────┬───────────────────┬──────────┤
│ Структура     │     3D / 4D       │ Свойства │
│ проекта       │     Viewport      │          │
│               │                   │          │
├───────────────┴───────────────────┴──────────┤
│ Контекстная панель / история / timeline       │
└──────────────────────────────────────────────┘
```

Главный объект интерфейса — viewport.

Панели не должны визуально конкурировать с моделью.

---

# 14. Viewport

Viewport — центральная рабочая поверхность.

Он должен поддерживать:

- вращение;
- панорамирование;
- масштабирование;
- выделение;
- hover highlight;
- перемещение;
- удаление;
- создание;
- контекстные операции;
- работу с плоскостями;
- эскизы;
- 3D-модели;
- временную шкалу для 4D.

Viewport не должен зависеть от конкретной SwiftUI-композиции. Рендеринг остаётся отдельным слоем.

---

# 15. Выделение и контекст

Главное UX-правило:

> **Выбрал объект — получил только релевантные действия.**

При hover:

- лёгкая подсветка;
- без изменения геометрии;
- без резкого визуального шума.

При selection:

- устойчивое состояние;
- свойства объекта;
- доступные операции;
- история происхождения.

Контекстное меню должно показывать только допустимые действия.

---

# 16. Sketch UX

Эскиз — самостоятельная инженерная среда внутри MIR 4D.

Путь:

```text
Выбор плоскости
  ↓
Эскиз
  ↓
Геометрия
  ↓
Ограничения
  ↓
Размеры
  ↓
Проверка
  ↓
Операция
```

Необходимо поддерживать:

- линии;
- окружности;
- дуги;
- прямоугольники;
- полигоны;
- точки;
- trim/extend;
- offset;
- mirror;
- constraints;
- размеры;
- привязки;
- snap;
- undo/redo;
- визуальное состояние полностью определённого / недоопределённого эскиза.

---

# 17. Sketch Snap Engine

Snap должен быть контекстным.

При наведении показывать минимальный маркер:

- endpoint;
- midpoint;
- center;
- intersection;
- perpendicular;
- tangent;
- horizontal;
- vertical;
- grid.

Не показывать одновременно все возможные подсказки.

---

# 18. Properties UX

Properties Panel не должен быть постоянно заполненным справочником.

Если ничего не выбрано:

> Выберите объект.

Если выбран объект:

- основные параметры сверху;
- инженерные свойства ниже;
- расширенные свойства раскрываются по запросу.

Редактируемые значения должны быть явно отличимы от информационных.

---

# 19. История модели

История должна объяснять происхождение результата.

Пример:

```text
Эскиз 01
 ↓
Выдавливание 01
 ↓
Скругление 01
 ↓
Отверстие 01
```

Выбор операции должен позволять понять:

- что было создано;
- из чего;
- какие параметры использовались;
- что зависит от операции.

---

# 20. 4D UX

Четвёртое измерение МИР 4D — время.

Время не должно быть отдельной декоративной панелью.

Оно должно становиться рабочим параметром объекта и процесса.

Базовая модель:

```text
Геометрия + состояние + время = 4D объект
```

Timeline должен позволять:

- перемещаться по времени;
- видеть состояние модели;
- запускать/останавливать воспроизведение;
- задавать интервалы;
- связывать события с объектами;
- визуализировать изменения.

---

# 21. РитмАлго

Концепция времени МИР 4D развивается в направлении `РитмАлго`.

Время рассматривается как механизм обновления состояния системы:

```text
Такт
 ↓
Состояние
 ↓
Изменение
 ↓
Следующий такт
```

UX должен позволять в будущем визуализировать такой процесс без превращения интерфейса в сложную математическую панель.

---

# 22. AI UX

AI не должен быть отдельным набором десятков кнопок.

Главный пользовательский вход:

> **Спросить МИР**

AI получает контекст:

- выбранный объект;
- эскиз;
- геометрию;
- историю;
- параметры;
- ошибки;
- текущую рабочую область;
- при разрешении пользователя — проектный контекст.

Пример:

> Почему отверстие не симметрично?

Ответ должен основываться на реальном состоянии модели, а не только на тексте запроса.

---

# 23. AI Inspector

AI Inspector должен работать как помощник диагностики.

Он должен находить:

- геометрические ошибки;
- противоречивые constraints;
- недоопределённые эскизы;
- потенциальные проблемы B-Rep;
- проблемы параметров;
- ошибки проектного состояния;
- ошибки интеграции.

Но результаты должны быть представлены человеческим языком.

---

# 24. Анализ / CAE UX

CAE не должен загружать стартовый интерфейс.

Пользователь входит в анализ через контекст модели:

```text
Выбрать объект
 ↓
Анализ
 ↓
Материал
 ↓
Нагрузка / условия
 ↓
Расчёт
 ↓
Результат
```

Результаты должны возвращаться в знакомую модель/viewport.

---

# 25. Collaboration UX

Совместная работа не должна требовать отдельного «режима сервера» для обычного пользователя.

В будущем пользователь должен видеть:

- кто сейчас работает;
- что изменяется;
- комментарии;
- состояние синхронизации;
- конфликты;
- историю изменений.

Сложность Event Bus, Lamport clock и conflict resolution остаётся внутренней.

---

# 26. Комментарии и инженерные заметки

Комментарии должны быть привязаны к объектам и координатам, если контекст это позволяет.

Пользователь должен иметь возможность:

- добавить заметку;
- оставить комментарий;
- поставить стикер;
- указать требование;
- связать комментарий с моделью.

Это особенно важно для будущей web-платформы инженерных заказов.

---

# 27. Уведомления

Уведомления должны быть редкими и полезными.

Категории:

- успех;
- предупреждение;
- ошибка;
- информационное сообщение.

Нельзя использовать уведомления как основной способ навигации.

---

# 28. Анимация

Анимация должна объяснять изменение состояния.

Разрешены:

- появление;
- переход;
- подсветка;
- раскрытие;
- перемещение;
- запуск диагностики;
- переход Project Hub → CAD;
- возврат CAD → Project Hub.

Запрещено:

- постоянное декоративное движение, мешающее работе;
- чрезмерное свечение;
- анимация ради анимации;
- задержки, мешающие инженерному workflow.

---

# 29. Визуальный язык

Базовый стиль:

**industrial / engineering / precise / calm / modern**.

Основные свойства:

- тёмная рабочая среда;
- высокий контраст важных элементов;
- умеренное cyan/blue accent-направление;
- тонкие границы;
- небольшие радиусы;
- минимум декоративных градиентов;
- ясная типографика;
- визуальная иерархия.

Фирменная геометрия МИР 4D используется как акцент, а не как фоновой шум.

---

# 30. Цветовая логика

Цвет должен сообщать состояние.

- accent — действие / выбор;
- green — готово / успешно;
- yellow — предупреждение;
- red — ошибка;
- neutral — информация;
- white/gray — структура и текст.

Нельзя использовать множество цветов только для различения карточек.

---

# 31. Кнопки

Иерархия:

### Primary
Главное действие текущего контекста.

### Secondary
Важное, но не основное действие.

### Quiet
Второстепенное действие.

### Contextual
Появляется только при наличии соответствующего объекта/состояния.

На одном экране не должно быть нескольких визуально равных Primary действий без явной причины.

---

# 32. Панели

Панель должна существовать только если она помогает текущей задаче.

Панели должны быть:

- скрываемыми;
- изменяемыми по ширине;
- контекстными;
- восстанавливаемыми;
- независимыми от конкретной геометрии viewport.

---

# 33. Keyboard UX

Клавиатура — полноценный второй способ работы.

Минимально:

- Cmd+N — новый проект;
- Cmd+O — открыть;
- Cmd+S — сохранить;
- Cmd+Z — отменить;
- Cmd+Shift+Z — повторить;
- Cmd+F — поиск;
- Delete — удалить выбранное;
- Esc — отменить/закрыть контекст;
- Space — контекстно воспроизведение 4D/времени.

Горячие клавиши не должны конфликтовать с macOS без необходимости.

---

# 34. Drag & Drop

Поддержать:

- `.mir4d` → Project Hub;
- инженерные файлы → соответствующие импортёры;
- объекты внутри рабочих областей;
- будущие материалы/ресурсы.

Drag & Drop должен показывать допустимость действия до сброса.

---

# 35. Accessibility

MirUI должен учитывать:

- масштабирование интерфейса;
- читаемость;
- клавиатурную навигацию;
- контраст;
- понятные labels/help;
- отсутствие зависимости только от цвета.

---

# 36. Состояния интерфейса

Каждый основной экран обязан определить:

- loading;
- empty;
- ready;
- selected;
- editing;
- processing;
- success;
- warning;
- error;
- unavailable.

Не должно быть состояния, в котором UI просто «молчит».

---

# 37. Архитектурное правило MirUI

MirUI не должен напрямую знать детали реализации `MirEngine`.

Рекомендуемый поток:

```text
SwiftUI
  ↓
ViewModel / AppState
  ↓
Commands / Services
  ↓
Event Bus / Runtime boundary
  ↓
MirEngine
```

Для сервера:

```text
MirUI
  ↓
Client / Service
  ↓
MirServer
```

---

# 38. AppState

`AppState` является источником пользовательского состояния приложения.

Он должен управлять:

- текущей рабочей областью;
- выбранным объектом;
- состоянием проекта;
- навигацией;
- уведомлениями;
- состояниями UI.

View не должна превращаться в место хранения бизнес-логики.

---

# 39. Commands

Действия пользователя должны проходить через команды/сервисы.

Примеры:

- New Project;
- Open Project;
- Save Project;
- Close Project;
- Select Object;
- Delete Object;
- Create Sketch;
- Create Feature;
- Start Analysis;
- Start 4D;
- Ask MIR.

Команда должна быть повторно используемой из UI, клавиатуры, меню и будущего AI.

---

# 40. Event Bus

Event Bus обеспечивает слабую связанность компонентов.

UI должен реагировать на события:

- project activated;
- project saved;
- project closed;
- object selected;
- model changed;
- analysis completed;
- diagnostics changed;
- collaboration updated.

UI не должен вручную синхронизировать каждую подсистему с каждой.

---

# 41. Rendering boundary

SwiftUI отвечает за оболочку и интерфейс.

Рендереры отвечают за отображение инженерной сцены.

Необходимо сохранять разделение:

```text
SwiftUI UI
   │
   ├── panels
   ├── commands
   └── state

Viewport Renderer
   │
   └── 3D / 4D scene

MirEngine
   │
   └── geometry / math / simulation
```

---

# 42. Производительность

UX не должен создавать лишние вычисления.

Требования:

- не пересчитывать всю модель при изменении одного UI-состояния;
- избегать тяжёлых операций в `body` SwiftUI;
- использовать debounce для поиска;
- использовать фоновые задачи для IO/расчётов;
- не блокировать main thread;
- не загружать большие previews без необходимости.

---

# 43. Стабильность

Перед визуальными изменениями необходимо сохранять:

- существующие команды проектов;
- формат `.mir4d`;
- события;
- навигацию;
- работу `MirEngine`;
- текущие рабочие области.

UX-рефакторинг не должен превращаться в переписывание ядра.

---

# 44. Принцип «не ломать ядро»

Если UX-задачу можно решить в `MirUI`, изменение не должно переноситься в `MirEngine`.

`MirEngine` изменяется только если UI требует реально отсутствующей инженерной возможности.

# 47. Правило контекстной мощности

Любая сложная функция должна отвечать на три вопроса:

1. Когда она нужна?
2. Какой объект/состояние её активирует?
3. Как объяснить результат пользователю?

Если функция не имеет понятного контекста — она не должна появляться в основном UI.

---

# 48. Правило одного следующего шага

В каждый момент пользователь должен легко понимать следующий шаг.

Примеры:

```text
Выберите плоскость
→
Нарисуйте профиль
→
Завершите эскиз
→
Выберите операцию
```

или:

```text
Выберите деталь
→
Задайте материал
→
Задайте нагрузку
→
Запустите расчёт
```

---

# 49. Правило инженерной обратной связи

После каждого действия система должна сообщать состояние.

Например:

- `Эскиз создан`;
- `Операция построена`;
- `Проект сохранён`;
- `Constraint противоречит существующему`;
- `Расчёт завершён`.

Пользователь не должен гадать, произошло ли действие.

# 51. Критерии готовности MirUI

MirUI считается UX-готовым для релиза, если:

- новый пользователь понимает стартовый экран без инструкции;
- основной workflow проходит без поиска скрытых кнопок;
- UI не перегружен внутренними названиями подсистем;
- выбранный объект всегда имеет понятный контекст;
- ошибки объясняются и имеют следующий шаг;
- проект можно создать, открыть, сохранить и продолжить;
- viewport является главным рабочим пространством;
- Sketch workflow последователен;
- 4D встроено в модель времени, а не является декоративной вкладкой;
- AI работает через контекст;
- collaboration не требует понимания серверной архитектуры;
- MirUI не нарушает границы `MirEngine`.

# 52. Нормативные правила

### UX-001
Простота интерфейса важнее количества одновременно видимых функций.

### UX-002
Основной экран показывает задачи пользователя, а не архитектуру системы.

### UX-003
Каждый экран имеет один очевидный следующий шаг.

### UX-004
Главный viewport является центром инженерной работы.

### UX-005
Сложные функции открываются контекстно.

### UX-006
MirUI не должен напрямую зависеть от внутренних деталей MirEngine.

### UX-007
Состояние приложения является явным и наблюдаемым.

### UX-008
Любая длительная операция должна иметь обратную связь.

### UX-009
Ошибки должны объяснять причину и следующий шаг.

### UX-010
Анимация служит пониманию состояния, а не украшению.

### UX-011
AI является контекстным помощником, а не отдельным набором функций.

### UX-012
4D является временным состоянием инженерной модели.

### UX-013
Нельзя добавлять новую кнопку, если существующий контекст может выполнить ту же задачу.

### UX-014
UX-изменения не должны без необходимости затрагивать MirEngine.

### UX-015
Все новые подсистемы обязаны предоставлять понятный пользовательский сценарий до включения в основной интерфейс.

# 53. Итоговая философия

МИР 4D не должен быть программой, в которой пользователь ищет нужную кнопку.

Он должен быть средой, которая понимает текущий инженерный контекст и предлагает следующий логичный шаг.

```text
          МИР 4D
             │
       ┌─────┴─────┐
       │   Проект  │
       └─────┬─────┘
             │
       ┌─────┴─────┐
       │   Модель  │
       └─────┬─────┘
             │
      ┌──────┼──────┐
      │      │      │
    Эскиз  Анализ   4D
      │      │      │
      └──────┼──────┘
             │
          Результат
```

**MirUI — это не оболочка над MirEngine.**

Это пользовательский язык всей инженерной системы МИР 4D.

> **Пользователь говорит задачей. MirUI переводит задачу в действие. MirEngine выполняет инженерную работу. MirUI возвращает человеку понятный результат.**
